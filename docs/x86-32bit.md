# haikode on 32-bit Haiku (x86_gcc2 hybrid)

**Status: prepared, not yet verified on hardware.** Everything below follows
from source reading and the HaikuPorts recipes; the project's own rule — not
done until it runs on the machine — applies. This file is the runbook for
that verification, written so the test session only has to execute it.

## Why it should work

- The whole engine (agent loop, providers, tools, sessions, TUI, REPL) is
  Python 3 standard library. No ctypes, no struct packing, no pointer-size
  assumptions; Python integers are arbitrary precision.
- HaikuPorts builds python3.10 for 32-bit: the recipe declares
  `ARCHITECTURES="all !x86_gcc2"` with `SECONDARY_ARCHITECTURES="x86"` — the
  interpreter is compiled by the modern gcc for the hybrid's secondary
  architecture, and its commands are installed as plain `python3.10` in
  `bin/`, not `bin/x86/`.
- Memory is a non-issue: a 32-bit process address space is ~2 GB and haikode
  uses tens of MB. The heavy lifting happens at the provider's end.

## What is different on the hybrid, and already handled

| Concern | Handling |
|---|---|
| `uname -m` answers **BePC** (BeOS inheritance), not a valid hpkg arch | `build-hpkg.sh` uses `getarch`, maps BePC/x86_gcc2 → `x86` |
| Plain `gcc`/`g++` is the ancient gcc2, which cannot build our C++ | both build scripts run `make` under `setarch x86` on the hybrid |
| The Python package is *named* `python3.10_x86` | the hpkg requires `cmd:python3.10`, which both spellings provide |

## The live test, in order

Prerequisites on the machine: a 32-bit Haiku install (beta5 or newer) with
network. Everything else is installed in step 1.

```sh
# 1. dependencies
pkgman install python3.10 ca_root_certificates git

# 2. get the tree (any of: git clone, or the bare-repo deploy setup from
#    scripts/deploy-to-haiku.sh's comment block)
git clone <your-remote> /boot/home/haikode
cd /boot/home/haikode

# 3. the interpreter and its C modules
python3.10 -c "import ssl, sqlite3, curses; print('ok')"

# 4. the full suite — THE acceptance gate
HAIKODE_CONFIG_DIR=$HOME/e2e-32 python3.10 -m unittest discover -s tests -t . -p "test_*.py"
# expected: 2270 tests, exactly 5 failures, all in tests/test_wiring_audit.py
rm -rf $HOME/e2e-32

# 5. doctor + a $0 live turn (zen needs no key)
PYTHONPATH=/boot/home/haikode python3.10 -m haikode doctor
PYTHONPATH=/boot/home/haikode python3.10 -m haikode -p zen --no-tui "Say the single word: ok"

# 6. the TUI over a real pty
PYTHONPATH=/boot/home/haikode python3.10 tests/render_tui.py --help

# 7. native builds (needs: pkgman install haiku_devel make)
sh scripts/install-on-haiku.sh          # compiles hai-keystore + desktop via setarch
scripts/build-hpkg.sh                   # should produce build/haikode-*-x86.hpkg
pkgman install ./build/haikode-*-x86.hpkg
```

## What to record for the install report

Same shape as the x86_64 report (`haikode-hrev*-install-report.md`): Haiku
revision, `getarch` output, package versions, the suite's failure list
verbatim, and anything that needed a workaround. A failure unique to 32-bit
is a finding, not a disappointment — that is what the run is for.

## Known unknowns

- Whether `BKeyStore`/`hai-keystore` behaves identically on the hybrid
  (the API exists; the keyring-approval dialog flow is untested there).
- Whether the desktop app links cleanly under `setarch x86`
  (`-lbe -ltracker` exist for the secondary arch, but nobody has tried).
- Suite duration on old hardware — plan for several minutes, not two.
