verified by local experiment (E1/E2/E3) and independently reproduced

# Adversarial review v3: `persistent-connections.md` (v2) and the Kimi K3 review

Facts established locally before any claim below (experiments in `/tmp/fable-qa`, code read in full):

- **E1** — `ssl.SSLSocket.recv(n, flags≠0)` raises `ValueError("non-zero flags not allowed…")` (stdlib source, confirmed by execution). For HTTPS, `http.client`'s `conn.sock` *is* the SSLSocket. Rule 5's probe, written as specified, throws on every production connection.
- **E2** — On a socket with a timeout set, `recv(1, MSG_PEEK | MSG_DONTWAIT)` on a **healthy idle** peer blocks for the **full socket timeout** (measured: 2.002 s with `settimeout(2.0)`), then raises `socket.timeout`. CPython's timeout path selects for readability before the flag ever reaches the kernel. It returns `BlockingIOError` immediately only in non-blocking mode (`settimeout(0)`) or blocking-no-timeout mode. Every haikode socket has a timeout (`_SplitTimeoutMixin.connect`, net.py:249-251).
- **E3** — After a **graceful TLS close** (SSL_shutdown → close_notify → FIN, i.e. how a real provider edge idle-closes), a raw TCP-level peek returns **data** — `b'\x15\x03\x03...'`, the encrypted alert record — not `b''`. The `b'' == dead` check never fires for the graceful HTTPS close it exists to catch. `b''` appears only on a plaintext FIN with an empty buffer — which is exactly what the plain-HTTP test harness produces and production (all HTTPS) never does.
- **Caller map** — the "turn path" is not one function: `anthropic.py:146`, `openai_compat.py:176`, `gemini.py:187` use `stream_sse_events`, but **`subscription.py:237` calls `sse_json_events` directly, with the default `stop_on_done=False`**. And `request_json` (spec line 52) **does not exist anywhere in the codebase** — in a spec whose preamble boasts "every claim below carries a line reference that was checked."

## 1. Attack the v2 rules

**Rule 1 (aborted never reused) — right intent, unstated precedence against rule 2.** "Aborted" is undefined (abort event? stall? any early generator close?), and there is a real interleaving where rules 1 and 2 give opposite answers: the server delivers the whole tail in one burst, the pump drains to end-of-body and sets its flag, *then* the user aborts before the consumer drains the queue. Rule 2's letter ("released only if that flag is set") says release; rule 1's letter says never. The socket is at a clean HTTP boundary so release happens to be safe — meaning rule 1's own rationale ("a reader may still be inside OpenSSL", net.py:294-310) is false in this case and an implementer cannot tell which rule is authoritative. The spec presents nine absolutes and never states the actual release predicate, which must be one conjunction: *pump-flag ∧ consumer exited by clean StopIteration (not Aborted/NetError) ∧ ¬will_close ∧ slot free*.

**Rule 2 (release on pump's end-of-body flag) — the flag mechanism is sound, but only under three conditions the spec never states.** Answering the specific questions: *(i) Is the flag race-free?* As a plain bool it relies on the GIL; fine on Haiku's CPython, should be a `threading.Event` on principle. *(ii) Who reads it, under what lock?* The consumer, under **no** lock, in a `finally` — and there are **two** finallys, not one: `_iter_lines`' (net.py:548-550) *and* `sse_json_events`' (net.py:692-702), both of which unconditionally `_hard_close` today. The spec cites only the pump side; an implementer must discover the second disposal site themselves. (I traced the failure mode of missing it: after a fully-drained body `HTTPResponse._close_conn` has already severed `fp`, so the second `_hard_close` no-ops by luck — net.py:315 finds `fp=None`. The design survives on an undocumented accident of `http.client` internals. That is not a rule; it's a landmine with the pin still in.) *(iii) Can the pump set the flag after the caller decided to discard?* Yes — consumer reads flag=False, calls `_hard_close`; pump finishes the terminator microseconds later and sets the flag. This is benign (lost reuse, no corruption) **if and only if** discard is `_hard_close`'s parking discipline, a conditionality the rule never states. Also unstated: after flag-set the pump thread is alive but socket-quiescent (only `put(_EOF)` remains, a queue op) — so another thread may legitimately acquire the released connection *while the old pump thread still exists*. That is safe purely by code ordering (flag strictly after the last socket touch, net.py:512-519) which the spec must mandate, not assume. Finally, rule 2's whole framing is built on `stop_on_done=True` (net.py:722) — but the subscription turn path runs `stop_on_done=False` (subscription.py:237), where streams end at clean EOF and the pump provably finishes. The dominant reuse case for at least one first-class provider is the *easy* case, and the spec doesn't know it exists.

**Rule 3 (TTFB bounded by connect-scale budget) — implementable, but its letter invites the unimplementable reading.** The question "what interrupts the pump's readline at 15 s?" has a clean answer the spec never gives: *nothing needs to*, because the first byte is the **status line**, read inside `getresponse()` on the caller thread **before the pump exists** — the code order at net.py:678-679 (`_open` returns the response, then `_iter_lines` starts the thread) proves the enforcement point. Correct implementation: `sock.settimeout(TTFB)` before `getresponse()`, widen to the stall budget after it returns. But rule 3's letter says only "time to first byte," and an implementer who reads that as *first SSE byte/event* must interrupt a blocked readline cross-thread — impossible without violating rule 2's own no-inspection principle (`settimeout` from another thread does not affect an in-progress `recv`). One reading is unstated, the other is unimplementable. Additional gap: a 15 s TTFB cannot distinguish a black-holed link from a gateway that defers the status line until the upstream model responds (LiteLLM-style proxies do; users point `openai_compat.py` at such things). Those users get their turn killed at 15 s on every reused connection — and then rule 4 makes it worse (next).

**Rule 4 (invisible pre-first-byte retry) — four gaps.** *(i) Where is the body between attempts?* It's the `data` bytes built at net.py:664 — immutable, safe today; but `http.client.send()` consumes `read()`-ables (stdlib source quoted in the review at lines 235-248), so the day anyone passes a file-like body, the invisible retry silently re-sends an exhausted reader as an empty body. One sentence in the spec prevents that. *(ii) Can the abort fire between the failed first attempt and the invisible second?* **Yes, and the letter permits the retry to proceed anyway.** Today every attempt passes through `_open`'s `_check_abort` (net.py:425). The invisible retry lives below the retry loop; nothing in rule 4 requires an abort check before the second send. An abort landing during the 15 s TTFB wait is then followed by a full fresh request fired after cancellation — violating rule 8's spirit precisely ("cancellation stays instant"), with the request outliving the cancel. *(iii)* "Nothing was delivered" conflates delivery (response) with receipt (request): the write succeeded, the server may be mid-generation. This matches today's pre-commit retry semantics (a pre-first-event stall already re-sends, net.py:689), so it's not a *new* class — but rule 3 makes it *systematic* on slow-header providers, and invisible: no RetryPolicy attempt consumed means no backoff and no log entry for a double-submission. TTFB-timeout failures should consume a ladder attempt (visible); only deterministic-dead signals (EOF/RST/refused before any byte) deserve the invisible retry. *(iv) Scope:* "the stream path only" — but pooling hooked at `stream_sse_events` (net.py:705) misses `subscription.py:237` entirely. It must live at the `sse_json_events` layer, and the spec must say so, or the flagship provider gets nothing.

**Rule 5 (15 s cap + MSG_PEEK probe) — the probe is broken three independent ways, and the cap quietly guts the spec's own problem statement.** The probe: E1 (ValueError through the SSLSocket — the only socket object `http.client` hands you), E2 (done on the raw socket without `settimeout(0)` first, it blocks for the *leftover stall timeout* — up to 180 s — on every **healthy** acquire), E3 (`b''` is unreachable for graceful HTTPS close; close_notify presents as data, so the stated dead-detection never fires in production). A correct probe is: reach beneath the SSLSocket, `settimeout(0)`, raw `MSG_PEEK`, and treat **anything other than `BlockingIOError`** — `b''`, data, or ECONNRESET — as discard (pending bytes on an idle pooled TLS connection are close_notify or stray post-handshake records; discarding the rare healthy KeyUpdate is only churn). Note `settimeout(0)` also makes `MSG_DONTWAIT` redundant, which conveniently sidesteps the unanswered question of whether Haiku's stack honors that flag at all — this module's docstring is a monument to Haiku socket deviations (net.py:300-310); nobody has verified this one on Haiku. **The cap:** the spec's headline benefit is "an established, idle TCP connection survives a wifi down/reassociation window" — a window net.py:124-127 itself describes as *tens of seconds*. A connection idle through such a window is idle > 15 s, so rule 5 **discards it at acquire** and haikode fresh-connects into the dead window exactly as today. Under its own rules, pooling helps only flaps shorter than ~15 s landing inside an active tool loop, plus handshake latency. The vendor comparison in "The problem" (one connection held *across turns*) is structurally unreachable: vendors do it with HTTP/2 PING keepalives, which the spec explicitly excludes. The problem statement promises a benefit the rules preclude, and no one — not v1, not Kimi, not v2 — noticed.

**Rule 6 (never release `will_close`) — sound.** The one clean rule.

**Rule 7 (thread safety) — sound but incomplete:** it never says what happens when a release finds the slot occupied (two subagents to one host both finishing). Discarding the loser via a plain `close()` is actually safe *here* (no pump exists on a released connection) but collides with rule 8's blanket "teardown parks rather than closes" — the letters of 7 and 8 disagree about whether a healthy, pump-free connection may be plainly closed.

**Rule 8 (cancellation instant, park at exit) — the exit half is right; the cancellation half is satisfiable in letter while cancellation gets worse in fact.** The abort *path* stays instant, but the abort-**blind** window on the turn thread grows: today it's the connect window (≤20 s, abort checked only at net.py:425); pooled worst-case is TTFB (15 s) + invisible-retry connect (20 s) + fresh getresponse under the stall budget — during none of which anybody polls the abort. The rule as written would pass review while the user's Ctrl-C takes visibly longer to bite at turn start.

**Rule 9 (abandon urllib) — correct and verified (do_open forces `Connection: close` and closes the socket under the response), but it silently discards the error path too.** Today 4xx/5xx arrive as `urllib.error.HTTPError` and net.py:429-440 *reads the error body*. The http.client rewrite must rebuild that — and must **drain-and-release** error responses: a 429 arrives on a perfectly healthy connection, and an implementation that discards every non-200 will re-handshake in a retry storm at exactly the moment the provider asked it to slow down. Also "uses neither [redirects nor proxies]… stated in code" should be *checked* in code: if `https_proxy` is set, bypass the pool — a comment doesn't stop a corporate-proxy user's traffic from silently going direct; and custom `openai_compat` base URLs do hit real 3xxs, which should surface as an actionable NetError, not a bare status.

## 2. Attack Kimi's review

**"After the first byte flows, the connection is proven alive; death afterward is equally likely on fresh or reused" — an assumption dressed as a refutation.** "Proven alive" at byte 1 says nothing about the death distribution at byte N; the real question is whether reuse *shifts* that distribution, and it does wherever a death mechanism depends on connection **age** rather than idleness: LB max-connection-lifetime policies (Envoy `max_connection_duration` and kin), `keepalive_requests`-style caps, carrier-NAT table evictions under pressure preferring old flows. A pooled connection is strictly older at every point of its stream than a fresh one at the same point. Most such mechanisms cut gracefully at response boundaries (caught by rule 6) — but the hard variants cut mid-stream, and a mid-stream death lands on the committed rule (net.py:673, 682, 689): **unretryable, a fully-paid broken turn**, the single failure class the layer above cannot heal. The honest claim is "no mechanism known to us," the magnitude is probably small at the major providers — but "refuted" was overclaimed, and neither the spec's proof plan nor the field measurement counts broken-committed-turns, so if this is nonzero it ships invisible.

**"MSG_PEEK probe reliable / a dead-while-pooled connection is *deterministically* detectable" — falsified on three axes** (E1, E2, E3 above). Kimi's verification was plaintext loopback in blocking-no-timeout mode — the one socket mode haikode never uses, on the one protocol production never speaks. The two qualifiers vanished in the summary line, and v2 then baked the exact probe, `b''` claim included, into rule 5. This is a first review's experiment laundering into a spec rule with its lab conditions stripped. On Haiku specifically: `MSG_DONTWAIT`'s behavior is unverified on the only platform this ships to, and given this codebase exists because Haiku's `recv()` ignores `shutdown()` (net.py:300-310), "it's POSIX, it'll be fine" is not an argument this project is allowed to make. **For a silently dead peer (no FIN):** the probe returns `BlockingIOError` — *looks alive*. It is structurally blind to the black-hole case, i.e. to the motivating field scenario; Kimi's claim that the probe "makes Rule 4 nearly dead code" is therefore wrong — on flaky wifi the probe never fires and rules 3/4 remain the hot path.

**TLS-layer state: Kimi wrote "TLS session / certificate state — reusing HTTPSConnection is fine. Skip." (review line 117).** Inside that skip lived both the close_notify-defeats-`b''` finding and the SSLSocket-refuses-flags finding — the two facts that break rule 5. For the mid-record question specifically: a *previous* stream cut mid-TLS-record is covered (rule 1 discards it), and a *fully pumped* body implies SSL consumed whole records, so release is record-aligned; the residual case — partial next record (a truncated close_notify) seated in the TCP buffer at release — makes the *next* borrower's first SSL read fail or hang into the TTFB budget. Covered by rule 3, inefficiently; would have been worth one sentence. The skip is where the review's rigor ran out, and it's precisely the layer the whole design lives on.

Credit where due: the TTFB kill shot is real and decisive, the `post_json` replay catch is real, the pump-vouches rule is the right mechanism, and the do_open verification was properly done. But three of the review's conclusions that v2 absorbed verbatim — the probe, the 30→15 s cap tightening, and "equally likely after first byte" — were respectively wrong, benefit-destroying (Kimi tightened the cap purely from the provider-timeout side without noticing every second cut from the cap is a second cut from the survival window the spec is *for*), and unproven.

## 3. The measurement gate

The gate — count `failures.log` entries over a session with the 120 s ladder in place — is not decisive in either direction.

**It can pass (zero entries) while the problem remains.** `failures.log` counts post-ladder *final failures*. The ladder's success mode is a silent 10–120 s stall of visible retries — precisely the UX gap versus the vendor clients that motivated the spec. Zero entries is fully compatible with "haikode freezes and churns for a minute where codex sails through." The gate measures "does the ladder avoid *errors*," not "does the user experience the failure," so a pass would kill the spec while its motivation stands. The right metrics are turn-start latency distribution and retry-attempt counts around link flaps, with induced flaps (scripted down/up cycles) and a request-count denominator — a single organic session has no statistical power at all.

**It can fail while pooling wouldn't help — twice over.** First, windows longer than 120 s produce entries that pooling also can't fix (rule 3 fails the pooled connection fast into the same exhausted ladder). Second, and worse: **net.py:444 classifies every `socket.gaierror` as fatal** — including `EAI_AGAIN`, the canonical transient resolver error during a link-down window. If the flaky driver's failures manifest at the DNS step (likely on Haiku, which has no resolver cache to hide it), entries appear *without the ladder ever running*, the spec's own claim that failures are "ECONNREFUSED / EHOSTUNREACH" (spec lines 25-26) is wrong about the field mode, and the honest fix is a one-line retryable classification of `EAI_AGAIN` — not a connection pool. The gate counts entries; it never classifies them by mode, so it cannot distinguish "ladder insufficient" from "ladder never engaged because of a misclassification bug."

**And the gate never asks the question rule 5 raises:** what fraction of inter-request gaps at failure time is under 15 s? If most flaps hit connections older than the cap — and "tens of seconds" windows between user turns say they will — pooling delivers nothing regardless of what `failures.log` shows. That distribution is measurable from the same session logs and is the actual go/no-go number.

## 4. Verdict

**GO-WITH-CHANGES** — with the caveat that changes 1 and 2 are capable of flipping this to NO-GO once measured honestly, and should be executed in this order:

1. **Reconcile rule 5's 15 s cap with the problem statement, and redefine the gate.** State what pooling can actually deliver under a 15 s cap (short flaps inside active tool loops + handshake savings, *not* cross-turn survival); gate on turn-start latency, failure-mode classification, and the inter-request-gap distribution — and fix the `EAI_AGAIN`-is-fatal misclassification (net.py:444) *first*, since it may be the real field bug at 1/100th the risk.
2. **Rewrite rule 5's probe:** beneath the SSLSocket, `settimeout(0)` first, raw `MSG_PEEK`, *any* signal other than `BlockingIOError` discards; drop `MSG_DONTWAIT` (redundant in non-blocking mode, unverified on Haiku). As specified today it raises `ValueError` on every production connection while passing every plaintext test.
3. **Fix rule 4:** hook at `sse_json_events` (or `subscription.py:237` gets nothing); mandatory `_check_abort` before the invisible second attempt; TTFB-timeouts consume a visible ladder attempt, only deterministic-dead signals (EOF/RST/refused pre-byte) get the invisible retry.
4. **State rule 3's enforcement point:** first byte = status line, enforced by `settimeout(TTFB)` around `getresponse()` on the caller thread before the pump exists; widen to stall after. Kill the "first event" misreading explicitly.
5. **State the single release predicate** (pump-flag ∧ clean StopIteration ∧ ¬aborted ∧ ¬will_close ∧ slot free), resolving the rule 1/2 precedence conflict, and name **both** disposal sites (net.py:548-550 *and* net.py:692-702).
6. **Rule 9 completions:** 4xx/5xx bodies drained then *released* (429s must not trigger re-handshake storms); proxy env vars checked at runtime with pool bypass; 3xx surfaced as actionable NetError.
7. **Add a TLS variant of the test harness** for probe/release/acquire tests — every current proof runs plaintext, where `b''` works and close_notify doesn't exist.
8. Housekeeping: `request_json` doesn't exist (spec line 52); add the broken-committed-turn count to the field measurement.

If I were implementing this following all nine rules as written, the bug I would most likely write is **rule 5's probe, verbatim**: `conn.sock.recv(1, MSG_PEEK | MSG_DONTWAIT)` — which raises `ValueError` on every HTTPS connection because `conn.sock` is an SSLSocket; my defensive `except OSError`/broad-except around a socket probe would classify the "failed" probe as a dead connection and discard it, so the pool would silently discard every pooled connection in production and reuse would never happen — while every test in the proof plan passes green, because the harness speaks plain HTTP where the probe works exactly as the spec describes. The hardware before/after would then show "pooling changed nothing," and the spec would be judged a failure for a reason that was never true. The second-most-likely bug is the same probe minus the ValueError: run on the raw socket without `settimeout(0)`, it blocks every healthy acquire for the released connection's leftover 180 s stall timeout — turning the pool's happy path into a hang three times longer than the failure it was built to prevent.
